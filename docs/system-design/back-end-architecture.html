系统设计 · 后端

Yato 后端架构

后端的进程拓扑、目录结构、依赖方向与边界强制方式。进程的四类划分沿用 docs/system-design/iam.md 已定的模型；本文补齐它未覆盖的部分—— 每类进程内部该长什么样、谁能依赖谁、以及怎么让构建系统替你把这条线守住。

四条原则

其余所有决策由此推导
原则 01

领域逻辑只住在 service

BFF 和 worker 是消费者，不是领域的所有者。任何一条业务规则出现在 BFF 里，都是放错了位置。

原则 02

依赖单向，永不回调

admin / apiserver / worker 调用 service；service 不调用它们。这条线一旦被破，信任边界就没了。

原则 03

BFF 之间不互相调用

两个 BFF 若需要同一段逻辑，那段逻辑就不属于任何一个 BFF——它该下沉到 service。

原则 04

边界由构建系统强制

约定写在文档里会被遗忘，写在 visibility 里会在构建期报错。架构要能被机器拒绝。

proto 放顶层 apis/，不放 back-end/ 内

契约是跨语言的（前端、第三方都可能生成），不是 Go 内部实现。你顶层的 apis/ 目录已经存在且为空， 正好是它的位置。iam.md §4 写的是 backend/apis/iam/，与顶层目录冲突——需要二选一， 建议以顶层为准并更新文档。

三类进程的内部结构

这是当前最需要明确的部分

service

领域的所有者 · 唯一有 domain 的地方

✓domain — 实体、规则、仓储接口
✓usecase — 编排
✓adapter — gRPC 入站
✓infra — PG / IdP

BFF

聚合与整形 · 没有领域

✗domain — 出现即说明逻辑放错了位置
✗usecase — 同上
✓gateway — HTTP 入站 + 转码
✓client — RPC 出站

worker

异步消费与调度 · 没有领域

✗domain — 与 BFF 同理
✓job — 任务编排（薄）
✓client — RPC 出站

现在 back-end/app/admin/main/manager/internal/ 里有 domain/——这是矛盾的

iam.md §1.1 说 admin 是 BFF，§4 说 6 个子域"在 Go 层共进程、共享数据库"—— 也就是说领域逻辑的归属地是 service/。 一个只负责调 RPC 再聚合的 BFF，不该有自己的 domain。 那四个 provider.go 目前都是空的 wire.NewSet()，所以现在是调整的最佳时机： 趁里面还没有代码，把 domain 下沉到 service/iam。

两份 sso 在这里自动收敛

back-end/library/sso/（空 package）与 manager/pkg/sso/（有 New()）的分裂， 按这个架构只有一个答案：IdP 是 iam 的 provisioning 子域， 它属于 service/iam/internal/。框架层不许有业务域知识，所以 library/sso/ 应当删除。

依赖规则

原则 02 / 03 的操作化
从到允许理由
app/*service/* ✓唯一的上游 → 下游方向，经生成的 RPC client
service/iamservice/其他 ✓peer 服务对等调用，但禁止成环
app/adminapp/apiserver ✗BFF 之间不互相调用；共享逻辑下沉 service
app/*app/*/internal/** ✗internal 私有；Go 编译器已挡，Bazel 再挡一次跨 app
library/*app/* ✗框架不许知道业务；反向依赖是最难拆的一种
app/*library/* ✓单向
任何app/*/pkg/** ⚠只有显式标记为公开的才可依赖；默认应视为私有

让构建系统替你守边界

原则 04

上面那张表如果只写在文档里，半年后就会被绕过。Bazel 的 visibility 把同一条规则变成 构建期错误——违反时是 bazel build 失败，不是评审时的一句提醒。 这正是这个 monorepo 目前完全没用到、而性价比最高的能力（全仓没有一个 package_group）。 

# back-end/app/admin/BUILD.bazel
package_group(
    name = "admin",
    packages = ["//back-end/app/admin/..."],
)

# back-end/app/apiserver/BUILD.bazel —— 对称地声明自己
package_group(
    name = "apiserver",
    packages = ["//back-end/app/apiserver/..."],
)

# back-end/library/framework/BUILD.bazel —— 框架对全后端可见，但看不到任何 app
go_library(
    name = "framework",
    visibility = ["//back-end:__subpackages__"],
    # 依赖列表里不会、也不允许出现 //back-end/app/...
)

关键在最后一段注释：library/ 的 visibility 只向下开放， 它的 deps 里一旦出现 //back-end/app/...，Bazel 立刻报错。 「框架不许依赖业务」这条原则从口头约定变成了编译器保证。

framework 的边界

你们 README 里有几项该砍
能力归属说明
DI 装配 · Transport 生命周期✓ framework app.go / transport.go 已有雏形，方向对
日志 · 配置 · 遥测✓ framework log/ 已是真实实现
REST / RPC server 抽象✓ framework rest/ rpc/ 目前是空壳，需要填
client 拦截器（超时、重试、指标）✓ framework 只做进程内可完成的，跨进程的交给基础设施
服务发现 · 负载均衡✗ 砍掉 k8s Service + DNS 已经提供，自建是重复造且必然更差
限流 · 熔断✗ 砍掉 k8s / Ingress / Service Mesh 层承担；进程内做会与基础设施打架
健康检查端点✗ 砍掉 k8s 探针的标准做法，框架不必包一层

框架的能力应当按需生长

你们 framework/README.md 列了 14 项能力（discovery、loadbalance、circuitbreak、limit…）。 其中至少三项 k8s 已经免费给了。在 2 人规模、单集群的前提下， 先把「一个进程能起来、能优雅退出、日志能用、RPC 能通」这四件事做扎实， 其余等真实需求出现再加。一个半成品的自研服务网格，比没有服务网格更贵。

落地顺序

有依赖关系，按序执行

  1. 对齐文档与目录

    删掉空的 back-end/gateway/；app/interface → apiserver、 app/job → worker；决定 admin 是一个进程还是两个 （manager + member 目前文档里没有对应）。同步更新 iam.md §1.1。

  2. 定 proto 归属

    在顶层 apis/ 与 iam.md §4 的 backend/apis/ 之间二选一，建议顶层。 这一步必须在写第一行 proto 之前完成，否则生成路径会散落两处。

  3. 趁 internal 还是空的，把 domain 归位

    把 app/admin/main/manager/internal/domain/ 的定位想清楚并下沉到 service/iam。现在四个 provider.go 都是空 NewSet()， 这是零成本的窗口期。

  4. 打通一条端到端链路

    iam 的 auth 子域一个 proto → service/iam 进程（wire 注入）→ admin BFF 调通它。其余子域全部暂缓——先有一条真的通的， 比有六个半成品值钱（当前 22 个 BUILD.bazel 里只有 8 个有内容，一个 go_binary 都没有）。

  5. 加上 visibility 规则

    在链路通了之后做——你需要真实的依赖关系才知道边界画在哪。按上一节的 package_group 落地。

  6. framework 按需补齐

    先补 rest/ 与 rpc/ 的空壳，砍掉 discovery / loadbalance / limit。

进程的四类划分与信任方向来自 docs/system-design/iam.md §1.1 / §3 / §4，此处沿用未作改动； 目录结构、层内职责划分、依赖规则与 visibility 强制方式为本文新增。第 3、4 步涉及现有文件调整，动手前请确认。
